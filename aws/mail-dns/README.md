# Migadu DNS setup

The E-mail & DNS page now supports previewing and applying Migadu mail records in Route 53, followed by explicit Migadu activation. Mailboxes remain managed by the existing Supabase `migadu-admin` function. This service never receives the management key or mailbox passwords.

## Operating flow

1. Connect a dedicated Migadu management API key in Vedantix (My Account > API Keys in Migadu).
2. Choose a registered Vedantix domain; add it to Migadu if needed.
3. Open DNS instellen. Review the current and proposed records, then confirm the intended domain and apply.
4. Check AWS processing. `PENDING` is not completion; `INSYNC` means Route 53 processed the batch, not that every recursive resolver refreshed its cache.
5. Validate/activate with Migadu. Retry this read/activation check later if propagation is still pending. Do not repeatedly re-apply the DNS batch.
6. Create/manage mailboxes from the same page. No mailbox or customer mail is created by deploying or testing this feature.

Supported domains/zones are explicitly listed in `build.py`. Adding a domain to Vedantix does not automatically grant this function rights to its zone; review and update both the environment mapping and IAM scope through the infrastructure template. External DNS providers retain manual instructions.

## Access and behavior

- API Gateway HTTP API in eu-west-1, Lambda `vedantix-mail-dns`, Python 3.13. No public Lambda Function URL.
- HTTP route authorization is implemented in Lambda: call Supabase `/auth/v1/user`, then the existing `is_staff(ADMIN)` RPC on **every** request. Never trust decoded JWT claims or the browser's session object as authorization. No AWS operation precedes authorization.
- Domain names come from the caller-authorized Supabase `domains` registry, not request input. Unknown body fields, including caller DNS records or hostnames, are rejected.
- Public Supabase publishable key only. No Supabase service key, AWS static credentials or Migadu key in the function. The existing Vault-backed Migadu function supplies fresh authoritative records with the caller's verified session.
- HTTPS redirects are disabled so authorization cannot follow a redirect. CORS permits only the two production site origins; CORS is not the authentication mechanism.
- IAM SDK actions generated by IAM Policy Autopilot and then deterministically restricted to the three configured zone ARNs, mail record names, MX/TXT/CNAME types and CREATE/DELETE actions. Missing multivalue condition context fails closed. A/AAAA/NS/SOA and arbitrary zone changes are denied.
- The API verifies the public zone and compares public NS answers with its Route 53 delegation set.
- Existing MX from another provider, incompatible or duplicate SPF, conflicting DKIM, delegated subtrees, routing policies and malformed DMARC block **the entire batch**. Mail migration and merging other SPF senders require separate review.
- Existing strict/custom DMARC and unrelated TXT verification values are preserved. Existing TTLs are preserved.
- Apply re-fetches both providers and requires the preview fingerprint and exact domain confirmation. Exact DELETE plus CREATE in one transactional batch detects concurrent edits; no blind UPSERT, no write retries. A successful repeat preview is a no-op. A timeout has an uncertain outcome: refresh before retrying.
- Route 53 acceptance and final Migadu activation remain separate UI states. Status queries are bound to the chosen domain by the batch comment.
- CloudWatch audit events record verified actor, domain, request ID, proposal, before/after DNS values, and accepted change ID; uncertain writes are marked. No session, API key, password, request body or raw exception is logged. Retention: 365 days; log group retained on stack deletion. DNS record values are public; logs have normal administrator-only AWS access.
- API throttling: 10 requests/second, burst 20. Function timeout 29 seconds; writes are not started with less than five seconds remaining. AWS SDK attempts each operation once. The account's low regional concurrency quota does not allow a separate reserved allocation.

## Build, test and deployment

```sh
python3 -m pip install boto3
python3 -m unittest discover -s aws/mail-dns -p 'test_*.py' -v
python3 aws/mail-dns/build.py /tmp/vedantix-mail-dns
```

The build emits a CloudFormation bootstrap template, its scoped execution policy, and an `index.py` Lambda ZIP from the same source files. Bootstrap stack: `vedantix-mail-dns`. Configuration, API Gateway, invocation permission, role and log group are managed by the stack. Application code is updated by the existing production deploy workflow, before shipping the UI. That workflow runs tests again and updates only this Lambda's code, with narrow `GetFunctionConfiguration`/`UpdateFunctionCode` permissions added to its existing GitHub OIDC role. It cannot change the DNS execution role or API configuration. `.github/deploy-now` triggers deployment.

IAM baseline reproduction (absolute paths required):

```sh
uvx iam-policy-autopilot@latest generate-policies \
  "$(pwd)/aws/mail-dns/app.py" \
  --region eu-west-1 --account 381492205513 --service-hints route53 --pretty
```

Review action changes before replacing `autopilot-baseline.json`; `build.py` rejects an unexpected action set. Verified with the AWS policy simulator: intended mail batch allowed; A-record writes, wrong-domain names, missing condition context and UPSERT denied.

`node scripts/smoke-mail-dns.mjs` verifies live anonymous/invalid-session rejection, foreign-origin rejection, allowed preflight and method restrictions. Unit tests exercise mock authorized applications, replay/stale proposal rejection, conflicts, preservation, pagination and uncertain responses. These checks do not use a real admin token and do not alter DNS. Live provider end-to-end verification requires the user's Migadu key and an explicitly approved real setup action.

Rollback application code using a known previous ZIP; the deploy role cannot mutate infrastructure. Reverting this frontend feature does not undo customer DNS: do not revert live records without a separate reviewed migration. The audit contains the original values for investigation.
